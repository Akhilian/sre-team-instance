# 055 — Actions d'équipe ChatOps (panneau d'actions et compte « Ops »)
## Pourquoi
GOAL « monde DocShare piloté », tranche 2 : laisser des généralistes agir sur l'incident (contrôler, réindexer, revenir en arrière, redémarrer) en langage métier, sans kubectl ni PromQL, pour observer leurs biais face aux pannes. Le fil du canal sert de journal d'incident.
## Périmètre
- **Donnée** (`shared/types/scenario.ts`) : `Scenario.actions?: ScenarioAction[]`. `ScenarioAction = { id, label, type?: 'simulated' | 'index-check' | 'reindex' | 'changelog', delaySeconds?, startText?, doneText?, faults?: {name,value}[], text? }`. `simulated` (défaut) : message de démarrage `startText` immédiat, puis à `delaySeconds` appliquer `faults` via le client/registre de la 054 (même sémantique : registre mis à jour seulement si l'appel réussit) et poster `doneText`. `changelog` : poste `text` (narratif du scénario), sans délai. `index-check` et `reindex` : appels réels, libellés/textes de résultat fournis par DocShare (`summary`). Les 5 boutons du MVP ne sont que des entrées de donnée ; seul le `type` réel est codé.
- **Client** (`docshare-client.ts`, étendu) : `indexCheck()` = `GET /ops/index-check`, `startReindex()` = `POST /ops/reindex`, `getReindex()` = `GET /ops/reindex`, avec `X-Ops-Token` (jeton déjà prévu en 054). Mêmes erreurs génériques (ni jeton ni URL).
- **Serveur** : `server/utils/team-actions.ts` (exécuteur, dépendances injectées : client, horloge/timers, `postOps`) et routes `GET /api/actions` (liste `{id,label,type,running}` + `healthUrl?` ; vide/absent si pas de scénario `running` déclarant des `actions`) et `POST /api/actions/:id` (corps `{author}`). Réindexation : après `POST /ops/reindex`, sondage de `GET /ops/reindex` toutes les 5 s (injectable), un message Ops de progression (`processed/total`) à chaque changement de `processed`, message final à `state: done`, arrêt du sondage à `done` ou à l'arrêt du scénario.
- **Fil** : nouveau `Message.kind = 'ops'` (auteur affiché « Ops »), avec `ops?: { action: string, by: string, phase: 'start'|'progress'|'done'|'error' }` ; texte = message, heure = `createdAt` ; rendu en carte sobre (`OpsCard.vue`) montrant libellé, `by`, heure. Publié dans le canal d'incident du scénario (canal du premier message de scénario ; à défaut le canal par défaut). Rien d'autre n'est stocké.
- **Anti-doublon** : une action `simulated` en attente ou une réindexation en cours ne peut être relancée : `POST` renvoie 409 et poste (ou renvoie) un message Ops clair « <libellé> est déjà en cours » ; pour `reindex` en cours, aucun nouvel appel `POST /ops/reindex`, la progression courante (`GET /ops/reindex`) est affichée. Le panneau désactive le bouton d'une action `running`.
- **Panneau** (`ActionPanel.vue`) près de la saisie du canal d'incident : un bouton par action, tous visibles d'emblée, plus lien « Voir la santé du service » si `GRAFANA_DASHBOARD_URL` est défini (variable d'env, README + `render.yaml`, `sync: false` non requis ; absent sinon). Interrogation périodique de `GET /api/actions` pour l'état `running`.
- **Erreurs** : échec DocShare (désactivé, réseau, HTTP, timeout) → message Ops `phase:'error'` lisible (« Le service ne répond pas, réessayez dans un instant. »), sans URL, sans jeton ; l'action n'est plus `running`.
- **Cycle de vie** : `stop`/reset du scénario annulent timers et sondages en attente (aucun message Ops ni appel de panne après), vident l'état `running`.
## Hors périmètre
- Contenu du scénario (fiches PNJ, textes réels, alertes : tranche 3), débrief, multi-équipe, rôles/droits par action, authentification réelle de l'auteur (nom déclaré, comme les messages), câblage chart/plateforme (injection de `GRAFANA_DASHBOARD_URL`, `OPS_TOKEN`), déploiement, `kubectl`, persistance de l'état `running` au redémarrage, annulation d'une action en cours.
## Critères d'acceptation
- [x] CA1 — Client à fetch simulé : `indexCheck()`, `startReindex()`, `getReindex()` envoient respectivement `GET /ops/index-check`, `POST /ops/reindex`, `GET /ops/reindex` avec l'en-tête `X-Ops-Token` égal au jeton configuré ; sur non 2xx / rejet / sans `DOCSHARE_BASE_URL` l'erreur ne contient ni le jeton ni l'URL.
- [x] CA2 — Horloge simulée, action `simulated` (`delaySeconds:30`, `faults:[{name:'bad_release',value:0}]` avec panne active) : à l'appel un message Ops `phase:'start'` (texte `startText`, `by` = auteur) est publié immédiatement et le client n'a reçu aucun appel ; à t = 29 s rien d'autre ; à t = 30 s exactement un `setFault('bad_release',0)`, registre `isActive` faux et un message `phase:'done'` (texte `doneText`). Si `setFault` rejette : message `phase:'error'`, registre inchangé.
- [x] CA3 — Actions `index-check` et `reindex` à client simulé : le message Ops contient le `summary` retourné ; reindex : un seul `POST` puis un message de progression à chaque `processed` différent, message final à `done` et plus aucun sondage ensuite ; `changelog` poste `text` sans appel client.
- [x] CA4 — Anti-doublon : deuxième `POST /api/actions/:id` d'une action `simulated` en attente → 409, aucun second timer ni second `start` ; après l'échéance, relançable. Reindex déjà `running` : aucun second `POST /ops/reindex`, la progression est postée. `GET /api/actions` marque `running:true` pendant l'attente.
- [x] CA5 — Sans scénario `running`, ou avec un scénario sans `actions` : `GET /api/actions` renvoie une liste vide et `POST /api/actions/:id` répond 404 ; `ActionPanel` ne s'affiche pas (test de composant si l'outillage existe, sinon analyse du template). Après `stop()` ou reset au milieu d'un délai : à t dépassé, ni message Ops ni appel `setFault`, sondage de reindex arrêté.
- [x] CA6 — Non-fuite : ni `DOCSHARE_OPS_TOKEN` ni `DOCSHARE_BASE_URL` n'apparaît dans les réponses de `/api/actions*` ni dans les messages Ops publiés, y compris sur erreur ; le lien Grafana n'est présent dans la réponse que si `GRAFANA_DASHBOARD_URL` est défini.
- [ ] CA7 (à faire par chrome-checker, après redéploiement demandé par l'utilisateur) — Chrome (seul critère navigateur, instance Colima, sur demande) : lancer un scénario de test déclarant `actions`, le panneau montre les boutons ; un clic sur une action simulée affiche la carte Ops de démarrage puis, après le délai, celle de fin, bouton désactivé entre les deux.
## Écarts acceptés 2026-10-27
- (a) `GET /api/actions` renvoie aussi `channelId` : le panneau est limité au canal d'incident.
- (b) Le panneau disparaît quand le scénario passe à `finished` ; les timers en cours ne sont pas annulés par la fin naturelle. Acceptable pour 055. À retenir pour la tranche 3 : le scénario doit rester `running` jusqu'à la fin de séance (étape finale tardive) ou la règle sera corrigée.
- (c) Pas de tests de composant : CA5 (panneau absent) vérifié par analyse du template.

## Notes d'implémentation
Étendre le type `Message.kind` et le rendu (`MessageList`, chronologie/`/admin` à vérifier : un message `ops` ne doit pas casser les consommateurs de `kind`). L'exécuteur lit l'état du scénario via `getScenarioRun()` et réutilise `fault-state` + client de la 054 ; arrêt via le hook `onStop` existant. Sondage reindex : plafond de sécurité (ex. 10 min) puis message d'erreur.
